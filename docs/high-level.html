High-Level Detail

Black-box view of the orchestrator request path and the conditional routing logic that connects validation, classification, retrieval, clarification, generation, and formatting.

1. Request path — black box

Variant B — High-Level Black Box
flowchart TD Input((Input)) --> Validate[Validate] Validate -->|allowed| Classify[Classify] Validate -->|blocked| Refusal[Refusal] Classify -->|greeting / spec| Format[Format] Classify -->|question| Retrieve[Retrieve] Retrieve -->|needs clarification| Clarify[Clarify] Retrieve -->|continue| Generate[Generate] Generate --> Format Clarify --> Output((Output)) Refusal --> Output Format --> Output

A chat input is validated; blocked requests produce a refusal and exit. Allowed requests are classified: greetings/subspace specifications go straight to formatting, while real questions proceed to retrieval. Retrieval either emits a clarifying question (ambiguous) or continues to generation. Generation produces the answer, which is formatted with citations and returned as output.

  • Input → Validate: every chat completion request enters through input validation against Guardrails POST /v1/rails/check (stage=input).
  • Validate → Classify (allowed) | Refusal (blocked): the should_continue_after_validation conditional edge (graph.py:24) returns "format_refusal" when blocked is true, otherwise "classify".
  • Classify → Format (greeting/spec) | Retrieve (question): should_route_after_classify (graph.py:31) routes greeting/specification to format_response → End; real questions proceed to retrieval (directly, or via hybrid_classify when enabled).
  • Retrieve → Clarify (needs clarification) | Generate (continue): should_clarify (graph.py:45) splits retrieval: ambiguous queries emit a clarifying question; otherwise build context and generate.
  • Generate → Format → Output: guarded_generate calls Guardrails /v1/chat/completions → Gemma, then format_response adds citations and finish_reason.
  • Refusal → Output: format_refusal reuses format_response (graph.py:109, registered as a second alias) and ends the run.

2. Nodes and routing (high-level)

NodeResponsibility
validate_inputExtracts latest user message; calls Guardrails input rail /v1/rails/check (stage=input); sets blocked + refusal_message.
classifyLLM 3-way router: greeting / specification / question; sets applied_subspace for specifications; T5 scattered gate pre-sets needs_clarification.
hybrid_classifyTrained SVM-RBF classifier; escalates to Gemma via Guardrails when confidence below threshold (gated by hybrid_classifier_enabled); sets applied_subspace.
retrieveRewrites query against history; KB /search/api with metadata filtering (filter_path); T1–T7 recall fixes; FAQ verification; EntityList supplement; DLQ.
generate_clarificationLLM asks a short Persian disambiguating question listing the 4 subspaces; sets finish_reason="clarify".
build_contextNumbered sources ([1]..[20]) ≤14000 chars; system prompt (ICS credit scoring) + history + question; entity-list injection.
guarded_generatePOST Guardrails /v1/chat/completions (model gemma-4-31b-triton-trt); maps content_filter → blocked.
format_responseReturns {content, finish_reason, citations}; handles blocked, greeting, specification-ack, FAQ, G5 no-evidence refusal, faith/contradiction/subspace-mismatch guards.
format_refusalReuses format_response (graph.py registers it as a second alias under that name).

3. Graph wiring (conditional edges)

validate_input --(should_continue_after_validation)--> classify | format_refusal
classify       --(should_route_after_classify)-------> format_response | hybrid_classify | retrieve
hybrid_classify --> retrieve
retrieve       --(should_clarify)--------------------> generate_clarification | build_context
generate_clarification --> END
build_context --> guarded_generate --> format_response --> END
format_refusal --> END
format_response --> END
  • should_continue_after_validation(state) → "format_refusal" if blocked else "classify"
  • should_route_after_classify(state) → "format_response" if classify in ("greeting","specification") else "hybrid_classify" (when enabled) else "retrieve"
  • should_clarify(state) → "clarify" if needs_clarification or the T5 scattered/ambiguity safety net fires; else "continue"

Supplemental entity rows short-circuit clarify: when the entity tool matched a dictionary, the model can answer directly, so clarification is suppressed.

4. API contract (high-level)

MethodPathPurpose
GET/healthProcess health {"status":"ok"}
GET/readyDependency readiness for KB + Guardrails; ready only when both ready
GET/v1/modelsModel discovery (ics-helper-agent)
POST/v1/chat/completionsOpenAI-compatible chat entry point (streaming + non-streaming)

Non-streaming response includes rag metadata (request_id, citations, applied_subspace, available_subspaces, supplemental, follow_ups) and an optional audit trail. Streaming returns SSE data: chunks ending with data: [DONE]; the final chunk carries rag metadata and finish_reason (stop, content_filter, or clarify).

6. Tracing (Langfuse)

Every request creates a trace keyed by X-Request-ID with spans: validate_input, classify, query-rewrite, retrieve (+ supplement/fallback/DLQ/retry/broadened), build_context (+ compact), guarded_generate, format_response / generate_clarification, and a final trace-create upsert with output and metadata (citations, latency_ms, finish_reason). Falls back to the local JSONL collector at :3000 when Langfuse :3001 is unavailable.
